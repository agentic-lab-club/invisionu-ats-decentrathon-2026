7) Как собрать RAG быстро и без боли
------------------------------------

### Корпус

Раздели знания на 3 коллекции:

1.  **public\_university\_knowledge**  
    только публичный сайт и публичные PDF
2.  **admissions\_private**  
    внутренние admission docs / rubrics / process docs
3.  **student\_internal**  
    handbook, calendar, internal policies

### Обработка

Для каждой страницы сохраняй:

*   `title`
*   `url`
*   `audience = applicant | student | reviewer`
*   `language = ru | en | kz`
*   `page_type = faq | program | policy | contact | admission`
*   `last_seen_at`

### Chunking

Режь не просто по 500 символов, а **по секциям и подзаголовкам**:

*   один вопрос FAQ = один chunk
*   один program section = 1-3 chunks
*   admission steps = отдельный chunk
*   deadlines = отдельный chunk
*   mission / values = отдельный chunk

### Retrieval

На запрос “Какие программы бакалавриата есть?” фильтр должен сначала смотреть:

*   `audience=applicant`
*   `page_type in [program, faq, admission]`

На запрос “Как связаться с университетом?”:

*   `page_type=contact`

На запрос “Есть ли общежитие и stipend?”:

*   сначала `faq`
*   потом `foundation/undergraduate`
*   потом internal docs, если бот для студентов.

### Generation rules

Бот должен:

*   отвечать **только по найденным источникам**
*   показывать source titles / links
*   говорить “не нашёл в официальных данных”, если факта нет
*   не выдумывать scholarship details, housing details, deadlines

Про CloudFront для “сгенерированного URL” к сервисам
----------------------------------------------------

Это можно использовать, но с важной оговоркой.

**CloudFront подходит** для:

*   фронтенда,
*   API,
*   swagger `/docs`,
*   HTTP-based UI,
*   WebSocket-трафика.

CloudFront работает с **HTTP/HTTPS** custom origins и поддерживает **WebSocket**. Для custom origin можно указать HTTP/HTTPS порт, и CloudFront умеет маршрутизировать запросы по path pattern через cache behaviors. [AWS Documentation+4AWS Documentation+4AWS Documentation+4](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistS3AndCustomOrigins.html?utm_source=chatgpt.com)

Для тебя это означает:

*   **можно**: frontend, `/api/*`, `/docs/*`

*   **нельзя / не надо**: RabbitMQ AMQP `5672`, Postgres `5432`, внутренние FastAPI сервисы как сырой TCP-трафик

**AWS Secrets Manager сам по себе не “подсовывает” секреты в Docker Compose или в контейнеры.**  
Secrets Manager хранит секрет и отдаёт его через API, CLI, SDK или через локальный Secrets Manager Agent. Само получение секрета делается вызовом `GetSecretValue`, а на EC2 приложение или скрипт получает AWS credentials через **IAM role instance profile** из instance metadata. AWS CLI и SDK умеют автоматически брать эти временные credentials с EC2, если к инстансу прикреплена роль. [AWS Documentation+3AWS Documentation+3AWS Documentation+3](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_GetSecretValue.html?utm_source=chatgpt.com)

То есть логика такая:

**Secrets Manager** = хранилище секретов  
**IAM role на EC2** = право читать секреты  
**твой bootstrap/deploy/startup script** = достаёт секреты и уже сам передаёт их в `.env`, `config.prod.yaml` или напрямую в приложение. [AWS Documentation+2AWS Documentation+2](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_iam-policies.html?utm_source=chatgpt.com)

Самое важное понимание

На plain **EC2 + Docker Compose** это не работает как магия.

Насчёт SSH
----------

Раз ты не хочешь Session Manager и хочешь SSH — тогда просто открой `22/tcp` **не на весь мир**, а только на свой IP/CIDR. AWS отдельно предупреждает, что для SSH/RDP лучше разрешать доступ только с конкретных IP ranges, а не `0.0.0.0/0`. Насчёт API Gateway вместо Traefik
---------------------------------

Это **можно**, но только для **HTTP API**.  
API Gateway умеет проксировать запросы к любому routable HTTP endpoint, в том числе через HTTP proxy integration. [AWS Documentation+2AWS Documentation+2](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api.html?utm_source=chatgpt.com)

Но это хорошо подходит для:

*   Go API
*   swagger `/docs`

И **не подходит как замена внутренней сети** для:

*   Postgres
*   RabbitMQ AMQP
*   внутреннего контейнерного сервиса как “всё через API Gateway”

То есть если хочешь API Gateway:

*   направляй туда только **backend HTTP endpoints**
*   а всё остальное держи во внутреннем Docker network

1.2 Основные бизнес-сценарии
----------------------------

### Сценарий A. Подача заявки

1.  Applicant загружает файлы.
2.  Frontend вызывает `POST /uploads`.
3.  Backend грузит файлы в S3 и сохраняет metadata.
4.  Frontend вызывает `POST /applications`.
5.  Backend сохраняет user + application + file links + optional test answers.
6.  Backend публикует event в RabbitMQ: `application.submitted`.
7.  Applicant сразу получает ответ `202 Accepted`.

### Сценарий B. Транскрибация видео

1.  Go worker-consumer читает `application.submitted`.
2.  Генерирует presigned GET URL на video object в S3.
3.  Делает HTTP request в Whisper service.
4.  Сохраняет transcript в БД.
5.  Публикует `application.transcribed`.

### Сценарий C. AI scoring

1.  Go worker-consumer читает `application.transcribed`.
2.  Собирает scoring input:
    *   program,
    *   transcript,
    *   personality answers,
    *   file presence / portfolio presence,
    *   optional extracted text.
3.  Делает HTTP request в LLM Scoring service.
4.  Сохраняет scoring result.
5.  Обновляет статус заявки на `review_ready`.
6.  Публикует `application.scored`.

### Сценарий D. Работа комиссии

1.  Admin panel вызывает `GET /candidates`.
2.  Комиссия открывает кандидата через `GET /candidates/{id}`.
3.  Видит transcript, scores, evidence, weaknesses, flags.
4.  Меняет stage или decision через admin endpoint.

### Request

```
{
  "first_name": "Andrew",
  "last_name": "K",
  "phone_number": "+7701...",
  "email": "user@example.com",
  "password": "StrongPassword123"
}
```

### Logic

1.  проверить уникальность email
2.  создать пользователя с:
    *   `role = user`
    *   `is_email_verified = false`
3.  сгенерировать 6-значный код
4.  сохранить `code_hash` в `email_verification_codes`
5.  отправить код на email через SMTP

### Response

```
{
  "message": "Verification code sent to email"
}
```

`POST /auth/verify-email`
-------------------------

### Request

```
{
  "email": "user@example.com",
  "code": "123456"
}
```

### Logic

1.  найти пользователя
2.  найти активный неистёкший код
3.  сравнить hash
4.  отметить код как `consumed_at`
5.  поставить `is_email_verified = true`

* * *

`POST /auth/login`
------------------

### Request

```
{
  "email": "user@example.com",
  "password": "StrongPassword123"
}
```

### Logic

1.  найти пользователя
2.  проверить `password_hash`
3.  проверить `is_email_verified = true`
4.  выдать JWT access token

### Response

```
{
  "access_token": "jwt",
  "token_type": "Bearer"
}
```

Формат

### Required evaluative field

### Optional fields

`personality_test_answers` format

Logic of `POST /applications`
-----------------------------

1.  endpoint требует авторизацию `role=user`
2.  обновляет у пользователя:
    *   `first_name`
    *   `last_name`
    *   `phone_number`
3.  валидирует `program_code` через `programs`
4.  создаёт запись `applications`:
    *   `user_id`
    *   `program_id`
    *   `review_stage = initial_screening`
    *   `decision = pending`
    *   `submitted_at = now()`
5.  загружает video в S3
6.  создаёт `application_files` для video
7.  записывает `video_file_id` в `applications`
8.  если есть optional pdf — загружает их в S3 и создаёт `application_files`
9.  если переданы `personality_test_answers` — сохраняет в `application_test_answers`
10.  публикует RabbitMQ event:
    *   `application.submitted`
    11.  возвращает `application_id`

* * *

Response
--------

```
{
  "application_id": "uuid"
}
```

* * *

Business rules
--------------

*   без video заявка не создаётся
*   `program_code` должен существовать и быть `is_active = true`
*   один user может иметь только одну активную заявку
*   если у пользователя уже есть активная заявка, ручка возвращает ошибку

6) Async pipeline — обновлённая логика
======================================

Ты просил:

*   mp4 -> audio
*   audio -> Whisper
*   transcript -> scoring

* * *

RabbitMQ events
---------------

### 1\. `application.submitted`

Публикуется после `POST /applications`

Payload:

```
{
  "application_id": "uuid"
}
```

* * *

### 2\. Audio extraction worker

Backend worker:

1.  забирает заявку
2.  скачивает mp4 из S3
3.  извлекает audio
4.  загружает audio в S3
5.  создаёт `application_files` с `file_type = video_audio`
6.  пишет `video_audio_file_id` в `applications`
7.  публикует:

```
{
  "application_id": "uuid"
}
```

event:  
`application.audio_ready`

* * *

### 3\. Whisper worker

Backend worker:

1.  читает `application.audio_ready`
2.  получает audio object из S3
3.  вызывает Whisper HTTP API
4.  сохраняет transcript в `applications.video_transcript`
5.  публикует `application.transcribed`

* * *

### 4\. Scoring worker

Backend worker:

1.  читает `application.transcribed`
2.  собирает input:
    *   program
    *   transcript
    *   personality test answers
    *   optional file presence
3.  вызывает LLM Scoring HTTP API
4.  создаёт запись в `scoring_runs`
5.  обновляет:
    *   `applications.review_stage = application_review`
6.  публикует `application.scored`

* * *

### 5\. Error handling

Если упал любой шаг:

*   записать текст ошибки в `applications.screening_error`
*   stage оставить `initial_screening`

4.4 Applications
================

`POST /applications`
--------------------

Создание заявки по уже загруженным файлам.

### Request

```
{
  "first_name": "Andrew",
  "last_name": "K",
  "phone_number": "+7701...",
  "program_code": "undergrad_tech",
  "video_file_id": "uuid",
  "portfolio_file_id": "uuid",
  "english_result_file_id": "uuid",
  "certificate_file_id": "uuid",
  "personality_test_answers": [
    {
      "question_id": "uuid",
      "option_id": "uuid"
    }
  ]
}
```

* * *

Required fields
---------------

*   `first_name`
*   `last_name`
*   `phone_number`
*   `program_code`
*   `video_file_id`

Optional fields
---------------

*   `portfolio_file_id`
*   `english_result_file_id`
*   `certificate_file_id`
*   `personality_test_answers`

* * *

Logic
-----

1.  endpoint требует авторизацию `role=user`
2.  проверяет `is_email_verified = true`
3.  обновляет у `users`:
    *   `first_name`
    *   `last_name`
    *   `phone_number`
4.  валидирует `program_code`
5.  валидирует `video_file_id`:
    *   файл существует
    *   принадлежит current user
    *   `application_id IS NULL`
    *   `file_type = video_presentation`
6.  валидирует optional file ids аналогично
7.  создаёт `applications`:
    *   `user_id`
    *   `program_id`
    *   `review_stage = initial_screening`
    *   `decision = pending`
    *   `video_file_id`
    *   `submitted_at = now()`
8.  обновляет соответствующие `application_files.application_id = new_application_id`
9.  сохраняет `application_test_answers`
10.  публикует RabbitMQ event:
    *   `application.submitted`
    11.  возвращает `application_id`

* * *

Response
--------

```
{
  "application_id": "uuid"
}
```

* * *

Business rules
--------------

*   без `video_file_id` заявка не создаётся
*   файл должен быть загружен заранее через `/uploads`
*   нельзя передавать чужие `file_id`
*   `program_code` должен быть активным
*   один пользователь может иметь только одну активную заявку, если ты хочешь это ограничение в MVP

* * *

5) Async pipeline — обновлённая финальная логика
================================================

* * *

После `POST /applications`
--------------------------

Backend публикует event:

### `application.submitted`

```
{
  "application_id": "uuid"
}
```

* * *

Шаг 1 — audio extraction
------------------------

Worker:

1.  забирает mp4 по `video_file_id`
2.  извлекает audio
3.  грузит audio в S3
4.  создаёт `application_files` с `file_type = video_audio`
5.  пишет `applications.video_audio_file_id`
6.  публикует `application.audio_ready`

* * *

Шаг 2 — Whisper
---------------

Worker:

1.  читает `application.audio_ready`
2.  вызывает Whisper service
3.  сохраняет transcript в `applications.video_transcript`
4.  публикует `application.transcribed`

* * *

Шаг 3 — LLM scoring
-------------------

Worker:

1.  читает `application.transcribed`
2.  вызывает LLM Scoring service
3.  сохраняет запись в `scoring_runs`
4.  обновляет:
    *   `applications.review_stage = application_review`

* * *

Ошибки
------

Если любой шаг падает:

*   `applications.screening_error = error_text`
*   `applications.review_stage` остаётся `initial_screening`

* * *

6) Итог
=======

Итоговая модель теперь такая:

*   **нет `processing_status`**
*   **нет определения статуса по косвенным полям**
*   **только `review_stage` + `decision` + `screening_error`**
*   **`auth_codes` вместо `email_verification_codes`**
*   **register только по email/password**
*   **JWT TTL зафиксирован**
*   **`/uploads` обязателен**
*   **`POST /applications` принимает только `*_file_id`**

Это уже выглядит очень чисто и соответствует твоей логике MVP.
